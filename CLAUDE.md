# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Next.js web app plus a CLI, sharing code, that both bulk-import multiple-choice quiz questions into a Canvas LMS quiz via the Canvas REST API (`POST /courses/:course_id/quizzes/:quiz_id/questions`).

- **Web app** (`npm run dev` / `npm run build && npm start`): instructors log in via Canvas OAuth2, browse their courses/quizzes, upload a questions JSON file, review a validated preview table, select which questions to import (or "select all"), and import.
- **CLI** (`npm run cli -- <file.json>`): the original single-file tool, now with validation, a confirmation prompt, `--dry-run`, and colored output — still authenticates with a fixed Canvas personal access token from `.env`, unrelated to the web app's OAuth flow.

All application code lives under `src/`; root-level files are tooling config only (`package.json`, `next.config.mjs`, `jsconfig.json`, `.env*`).

The product/UI name is **CanvasTools** (the npm package is `canvas-tools`; the folder is still `tools/CanvasQuiz` — not renamed to avoid a disruptive path change). On `/courses`, `src/components/CourseBrowser.jsx` defaults to showing only favorited/starred Canvas courses (`is_favorite`, requested via `include[]=favorites` in `canvasClient.listCourses`), falling back to "Todos" only when the account has zero favorites — this is an intentional product default, not an oversight.

### Landing/cover page (`/`) — lives *inside* the dashboard, not before it

`src/app/(dashboard)/page.jsx` is the "capa" — the CanvasTools pitch plus a "what's built" vs. "future ideas" feature list — and it is a **protected dashboard page**, not a pre-login marketing page. `src/proxy.js`'s matcher includes the bare `'/'` (alongside `/courses/:path*` etc.) specifically so this page requires a valid session like every other dashboard route; an unauthenticated visit to `/` gets redirected to `/login` by the proxy before it ever renders. This means, post-login, `/` is reached three ways: clicking the sidebar logo (`Sidebar.jsx`'s `<Link href="/">`, not `/courses`), `/login`'s own already-authenticated redirect (now targets `/` instead of `/courses`), or typing the URL directly — in every case sidebar/topbar stay visible around it because it's a normal child of `(dashboard)/layout.jsx`. There is no more logic in `page.jsx` itself deciding where to send the user; that decision now lives entirely in the proxy + `/login`.

`/login` (outside the dashboard group, unauthenticated-reachable) intentionally shows **only** the existing Canvas-login card plus a `WebTechFooter` — no pitch, no feature list. That split — marketing content gated behind login, bare login+attribution before it — is the point of this whole structure; don't move the feature list back to a pre-auth page.

`src/components/WebTechFooter.jsx` is shared between `/login` and `(dashboard)/page.jsx` — one component, one place to update the WebTech copy/logo. `src/assets/images/webtech-logo.png` was downloaded from `https://webtech.network/logo.png` (WebTech's own official site) — like `logo.png`, it's a light/white-stroke mark on a transparent background, so it only reads against a dark backdrop; `.webtech-footer` in `globals.css` is a dark card (`--sidebar-bg`/`--sidebar-fg-soft`, the same permanently-dark palette the sidebar uses) precisely for that reason, rendered as a contained block wherever it appears rather than a full-bleed section. The logo is displayed at a fixed `width: 300px` (per explicit request — deliberately large for a footer mark, not a bug) with `height: auto` to preserve its aspect ratio.

### Dashboard shell (modeled on the Vercel Next.js admin dashboard template)

All authenticated pages live under the `src/app/(dashboard)/` route group (route groups don't affect the URL — `/courses` is still `/courses`), wrapped by `src/app/(dashboard)/layout.jsx`, which renders `src/components/Sidebar.jsx` (fixed dark icon rail — `'use client'` for `usePathname()` active-state) and `src/components/Topbar.jsx` (light bar with the logged-in user's name + a plain `<form method="POST">` logout button — no client JS needed there). `/login` and the root redirect `page.jsx` sit *outside* the group, so they render standalone with no sidebar/topbar chrome. The sidebar is deliberately always dark (`--sidebar-bg`/`--sidebar-fg` in `globals.css`, independent of the light/dark theme variables) because `src/assets/images/logo.png` is a light/white-stroke mark that isn't visible on a light background — don't let it start following `--paper`/`--ink`.

`src/proxy.js`'s matcher (`/courses/:path*`, `/api/canvas/:path*`) didn't need to change when the pages moved into the route group — route groups are purely organizational and invisible to routing/matchers.

Each dashboard page's `<main className="page">` wrapper doubles as the "card" surface (white background, border, shadow) sitting on the muted `--paper` background provided by `.dashboard-content` — this is why `.page` carries card-like styling in `globals.css` rather than each page rendering an explicit `<Card>` component.

On the courses table (`CourseBrowser.jsx`), each row is **not** a clickable link — the whole-row-as-link pattern was intentionally replaced with an explicit "Ver atividades" button in the actions cell, because more per-course actions are expected to land in that same cell later. Don't revert to a row-level `<Link>` wrapping the whole `<tr>`.

### Pending-grading visibility (`CourseBrowser.jsx` + `.../courses/[courseId]/atividades/`)

`CourseBrowser.jsx`'s table shows a **Pendências** badge (`course.needs_grading_count`, requested via `include[]=needs_grading_count` in `canvasClient.listCourses` — this is Canvas's own server-computed total, not something this app counts itself) and a `StatusIcon` (`src/components/StatusIcon.jsx`) derived from `course.workflow_state` (`available`→published, `unpublished`, `completed`). Its "Ver atividades" button leads to `src/app/(dashboard)/courses/[courseId]/atividades/page.jsx`, which lists the course's assignments (`canvasClient.listAssignments`) with their own `needs_grading_count`/`published`.

**Important gotcha**: only assignments with a truthy `quiz_id` (classic Quiz, `submission_types: ['online_quiz']`) get an "Importar questões" button, linking to the *unchanged* `courses/[courseId]/quizzes/[quizId]/import` route using `assignment.quiz_id` as the quiz id. Do **not** use `assignment.is_quiz_assignment` for this check — that field flags New Quizzes (LTI) assignments, which this app's import endpoint (`POST /courses/:id/quizzes/:quiz_id/questions`, a classic-Quizzes-only API) cannot target. There is no `courses/[courseId]/quizzes/page.jsx` list anymore — `atividades/` replaced it as the sole way to reach the import screen; `quizzes/[quizId]/import/page.jsx` itself was not touched.

This feature was ported from `tools/CanvasQuiz/ct/` — an **orphaned, unwired reference folder** (Express + jQuery/DataTables code meant for a different, absent host app; not required by anything in `src/`, not runnable standalone, uses env var names — `CANVAS_API_ENDPOINT`, `CANVAS_CLIENT_ID`, etc. — that don't exist in this app's `.env`). Only its two Canvas API calls and the "trust Canvas's own `needs_grading_count`" logic were reused; the DataTables/jQuery frontend and the per-section grading breakdown (`needs_grading_count_by_section`) were deliberately not ported. `ct/` itself was left in place, untouched, as read-only reference material.

### Rubric grading (`.../courses/[courseId]/assignments/[assignmentId]/grade/` + `RubricGrader.jsx`)

Every assignment row in `atividades/` gets a "Corrigir com rubrica" button (unconditional — unlike `quiz_id`, whether an assignment has an associated rubric isn't known from `listAssignments`' response, so the button always shows and the grading page itself renders a "sem rubrica" message when `assignment.rubric` is absent) linking to `courses/[courseId]/assignments/[assignmentId]/grade/page.jsx`. That page sequentially (never `Promise.all`, same reasoning as every other multi-call page in this app) fetches `getCourse` → `getAssignment` (a fresh single-assignment fetch, not whatever `listAssignments` already had — Canvas's own docs only confirm the `rubric` field's presence for the single-assignment show action) → `listSubmissions(..., { include: ['user', 'rubric_assessment'] })`, then hands `rubric` + `submissions` to `RubricGrader.jsx` (`'use client'`) — one big table, one row per student, one `<select>` per rubric criterion, pre-filled from each submission's existing `rubric_assessment` when present. Grades are submitted via `PUT /api/canvas/courses/[courseId]/assignments/[assignmentId]/submissions/[userId]`, built by `src/lib/rubricGrading.js`'s `buildGradePayload` into Canvas's real `rubric_assessment[criterion_id][points|rating_id|comments]` + `submission[posted_grade]` shape — not just a `posted_grade` plus a text comment, so Canvas's own rubric UI actually gets populated. Bulk "Enviar todas as notas" sends sequentially per row (same concurrent-Canvas-call race avoided everywhere else) after a confirm dialog, and skips any row with no criteria selected (to avoid accidentally zero-grading an unreviewed student).

This was ported from `RubricTool/` (repo root, sibling to `src/`) — a standalone, directly-runnable Express + vanilla-JS prototype (its own `package.json`/`server.js`/`public/`, unrelated to `ct/`'s "orphaned fragment" situation) that already solved this same workflow using a fixed personal-access-token instead of this app's OAuth session. Its single biggest gap, deliberately **not** carried over: it never sent Canvas a structured `rubric_assessment` at all — only a summed `posted_grade` plus a prose comment describing the rubric breakdown (built via a fragile string-marker-based merge in its `generateFeedback()`), so Canvas's own rubric grading UI was never actually populated. The big-table-of-students grading UX (one `<select>` per criterion, per-row "Nota Máxima"/"Limpar"/"Enviar", page-level "Enviar Todas" with a confirm) was kept; the Canvas-submission logic was rebuilt from Canvas's real API docs instead. `RubricTool/` itself was left in place, untouched, as read-only reference material — like `ct/`, but note it has its own live `.env` (a real Canvas personal access token) and `config.md` (same token, in scratch notes); both are excluded via root `.gitignore` (`.env`/`node_modules` were already caught by existing unanchored rules; `/RubricTool/config.md` needed an explicit entry). That token should be rotated since it sat in plaintext in the working tree.

### AI provider adapters (`src/lib/aiProviders/`) — 4 drivers, multiple named integrations per driver

Question generation (and any future AI-backed feature) goes through a small adapter architecture, not a single hardcoded OpenAI integration. Crucially, the adapter ("driver") layer is a different concept from an "integration": a driver is a protocol implementation (OpenAI/Gemini/Claude/Z.ai-shaped API calls); an integration (`public.ai_integrations`, see below) is a user-registered, named configuration — API key, base URL, model, prompt, sampling params — that picks one driver. A user can register any number of integrations per driver (e.g. two separate OpenAI integrations pointed at different keys/hosts) with zero code changes; only a genuinely new protocol needs a new driver module.

- **Adapter contract** — each driver module (`openai.js`, `gemini.js`, `claude.js`, `zai.js`) exports `id`, `label`, `defaultModel`, `async validateApiKey(apiKey, baseUrl?)` (→ `{ valid, error? }`), `async listModels(apiKey, baseUrl?)` (→ `[{ id, label }]`, see "User-selectable models" below), `async generateQuestions({ apiKey, baseUrl?, model, temperature?, maxTokens?, presencePenalty?, frequencyPenalty?, specs, systemPrompt? })` (→ a `quiz.schema.json`-shaped object), `async suggestReply({ ...same knobs, context, systemPrompt? })` (→ plain-text reply suggestion, used by `MessageList.jsx`'s "Sugerir resposta com IA"), and `async improveMessage({ ...same knobs, text, systemPrompt? })` (→ plain-text revised draft, used by `ComposeMessage.jsx`'s "Melhorar com IA" and `StudentMessageModal.jsx`). `baseUrl` lets one integration point its driver at any protocol-compatible host (e.g. an `openai` integration aimed at Groq/OpenRouter/Azure OpenAI/a self-hosted server) — this, not a new driver module, is how "new platforms" get added day-to-day. A driver whose API doesn't support a given sampling knob (Claude and Z.ai have no presence/frequency penalty concept) just ignores it, never throws. `systemPrompt` on all three defaults to that capability's own constant when omitted — see "Prompt customization" below. Adding a genuinely new driver means writing one module matching this contract (see `zai.js` for the simplest OpenAI-compatible reference) and adding it to the `PROVIDERS` array in `src/lib/aiProviders/index.js` — nothing else in the app changes.
- **`src/lib/aiProviders/index.js`** is the driver registry: `getProvider(id)` (throws on unknown id) and `listProviders()` (the id/label/defaultModel subset — used only to populate the "Provedor" `<select>` when creating an integration, never sent with any key).
- `openai.js` calls the Chat Completions API (`POST {baseUrl}/chat/completions`, `response_format: { type: 'json_schema', ... , strict: true }` for `generateQuestions`) rather than the Responses API — deliberately, so `temperature`/`max_tokens`/`presence_penalty`/`frequency_penalty` are native request fields and third-party "OpenAI-compatible" hosts (most of which only implement Chat Completions) work via `baseUrl`. `zai.js` (Z.ai / GLM models, `https://api.z.ai/api/paas/v4`) is structurally a close cousin of `openai.js` — same Chat Completions shape — but Z.ai's API only documents `response_format: { type: 'json_object' }` (no `json_schema`/strict mode) and has no presence/frequency penalty support or model-listing endpoint (`listModels` returns a hand-curated list in the module, not an API call).
- **`src/lib/aiProviders/shared.js`** (quiz generation), **`replyPrompt.js`** (reply suggestion), and **`improvePrompt.js`** (message improvement) each hold one capability's own system-prompt constant (`SYSTEM_PROMPT`/`REPLY_SYSTEM_PROMPT`/`IMPROVE_SYSTEM_PROMPT`) plus its user-message builder. `SYSTEM_PROMPT` is condensed from the `enade-it-questions` Claude Code skill, versioned in this repo at `skills/enade-it-questions/` (`SKILL.md` + `references/`) — **not** `~/.claude/skills/` (an earlier version of this doc pointed there; that path doesn't exist on a fresh machine). `skills/enade-it-questions/` is deliberately excluded from the root `/skills/*` gitignore rule (see `.gitignore`) specifically so it stays version-controlled, since it's the only surviving source of truth the condensed prompt can be checked against. `shared.js` also exports `buildUserMessage(specs)` and `buildQuizOutputSchema()`.
- `buildQuizOutputSchema()` strips `quiz.schema.json`'s `$defs.question.properties.answers.allOf` (the `contains`/`minContains`/`maxContains` mechanism enforcing "exactly one correct answer") and narrows `course_id`/`quiz_id` from `["integer","null"]` to plain `"integer"` (we always emit `0`, never `null`) — none of the vendors' structured-output/tool-input schema dialects reliably support that `allOf` combination. The "exactly one correct answer" rule becomes prompt guidance instead (see `SYSTEM_PROMPT`) and is re-checked after generation via `validateStructural()` in `src/app/api/ai/integrations/[id]/generate-questions/route.js` — same defense-in-depth pattern the Canvas import route already uses. There's no auto-retry: if it fails, the user just clicks "Gerar" again.
- Each driver feeds that same schema to its provider's structured-output feature differently, because the dialects aren't interchangeable: `openai.js` uses Chat Completions' strict `json_schema` `response_format` (schema enforced server-side by OpenAI); `claude.js` forces tool use (`tool_choice: { type: 'tool', name: 'emit_quiz' }`) with the schema as `input_schema`, and reads `toolUse.input` directly (Anthropic parses it for you, no `JSON.parse` needed); `gemini.js` and `zai.js` deliberately do **not** wire the schema into a native structured-output field (Gemini's `responseSchema` is proto-derived and easy to get subtly wrong from outside the SDK; Z.ai's API doesn't have an equivalent at all) — instead both only request JSON mode and describe the same schema as text in the prompt, relying on the shared post-generation validation as the real safety net.
- **Storage**: `public.ai_integrations` (Postgres/Supabase, one row per registered integration — **not** one row per provider) holds `provider` (driver id), `name`, `api_key_vault_id` (Supabase Vault, chave nunca em texto plano), `base_url`, `model`, `system_prompt`/`system_prompt_mode`, `temperature`, `max_tokens`, `presence_penalty`, `frequency_penalty`, `is_default`, `is_active` — see `supabase/volumes/db/manual/10_ai_integrations.sql` for the full DDL + `SECURITY DEFINER` RPCs (`create_ai_integration`/`update_ai_integration`/`delete_ai_integration`/`get_ai_integration`/`list_ai_integrations`, called only by `service_role`). `src/lib/aiIntegrations.js` wraps those RPCs for the app (`listAiIntegrations`/`getAiIntegration`/`createAiIntegration`/`updateAiIntegration`/`deleteAiIntegration`/`getConfiguredIntegrations`). This table has no auth-session involvement at all — access is keyed by the Supabase Auth user id, gated the same way as every other per-user table in this app (see "Two separate Canvas auth models" below; `src/lib/session.js`/iron-session is unrelated and only used by the GitHub/Google OAuth handoff).
- **Routes are integration-generic, not provider-generic**: `src/app/api/ai/integrations/route.js` (`GET` lists, `POST` creates — validates the key against the chosen driver first via `provider.validateApiKey(apiKey, baseUrl)`), `src/app/api/ai/integrations/[id]/route.js` (`PATCH` partial update — only re-validates the key when a new one is supplied in the body; `DELETE`), `.../[id]/models/route.js` (`GET`, mirrors the old per-provider models route but keyed by integration id), and `.../[id]/generate-questions|suggest-reply|improve-message/route.js` (`POST`, looks up the integration via `getAiIntegration`, which already returns the decrypted key + every saved parameter). No more `process.env['<PROVIDER>_MODEL']` deployment-wide fallback — with multiple integrations per driver a single env var per driver stopped making sense; each integration's own `model` (or the driver's hardcoded `defaultModel` when blank) is the only fallback chain now.
- `src/proxy.js`'s matcher includes `/questoes/:path*`, `/perfil/:path*`, and `/api/ai/:path*` alongside the Canvas-gated routes — an unauthenticated caller can't spend anyone's stored key, even though this feature doesn't touch Canvas or need token refresh to function.

### User-selectable models (`IntegrationManager.jsx`, `/api/ai/integrations/[id]/models`)

Each driver's own model-listing endpoint (already hit once for `validateApiKey`, now factored into `listModels(apiKey, baseUrl)`) is reused to let a professor pick which model an integration uses, instead of being stuck with `defaultModel`. `GET /api/ai/integrations/[id]/models` requires the integration's key to already be saved (reads it via `getAiIntegration`, never accepts a raw key in the request) and returns the filtered/normalized list; `IntegrationManager.jsx`'s per-card "Trocar modelo" picker fetches it lazily (only when expanded) and saves the choice via `PATCH /api/ai/integrations/[id]` (`{ model: '...' }`, or `{ model: null }` to reset to the driver default). The four drivers' list-models responses aren't interchangeable, so each adapter's `listModels` normalizes differently:
- **OpenAI** (`GET {baseUrl}/models`): returns *every* model OpenAI has — embeddings, whisper, tts, dall-e, moderation, chat — with no capability/type field to filter by. `openai.js` excludes non-chat ids via a regex heuristic (`NON_CHAT_MODEL_PATTERN`) and sorts by the response's own `created` timestamp, newest first. This heuristic can go stale as OpenAI ships new model families; if a clearly-non-chat model starts showing up in the picker (or a real chat model gets filtered out), update the pattern. A custom `baseUrl` pointed at a third-party host may not expose this endpoint at all, or may return a different model set — expected, not a bug.
- **Anthropic** (`GET {baseUrl}/models`): only ever lists Claude chat models, already newest-first — no filtering needed, just `?limit=100` to avoid the default page size of 20.
- **Gemini** (`GET {baseUrl}/models`): mixes in embedding/non-chat models too, but *does* expose a capability field — filtered to entries whose `supportedGenerationMethods` includes `generateContent` (the method this app's own adapter calls). Each model's `name` comes back as `models/gemini-2.0-flash`; stripped to the bare id form the rest of `gemini.js` already expects in its own `generateContent` URLs.
- **Z.ai**: no documented discovery endpoint at all — `zai.js`'s `listModels` returns a small hand-maintained list of known GLM model ids (see the module's own comment for where to re-check it).

### Questões (`src/app/(dashboard)/questoes/page.jsx` + `QuestionGenerator.jsx`)

Lets a professor pick a registered AI provider (a `<select>` only appears once more than one is configured — see below), list per-question specs (tema/nível/tipo — RU/CM/AR only, `INT` is never offered here), and get back a `quiz.schema.json`-shaped JSON they can preview and download.

- `questoes/page.jsx` passes `QuestionGenerator` the result of `getConfiguredIntegrations(user.id)` — active integrations with a key configured, formatted for the selector (`id`/`name`/`provider`/`providerLabel`/`model`/`isDefault`). If none are configured, it shows an alert linking to `/perfil` instead of the spec form.
- `QuestionGenerator.jsx`'s preview strips generated HTML down to plain text via `DOMParser(...).body.textContent` (never `dangerouslySetInnerHTML`) — this app has zero HTML-sanitization tooling, and AI-generated content is the first freeform content ever rendered here. The **saved JSON file** still contains the full, untouched HTML (that's what Canvas needs) — only the on-screen preview strips tags.
- `course_id`/`quiz_id` always generate as `0`, matching the skill's own convention for unset codes (never `null`, even though the schema itself permits `null`) — harmless downstream, since the existing import flow (`ImportQuestions.jsx` → `/api/canvas/import`) already ignores a file's own `course_id`/`quiz_id` in favor of the route's real `courseId`/`quizId`.
- `QuestionGenerator.jsx` always renders a "Gerar com a skill no Claude Desktop" card above the spec form (regardless of whether an AI provider key is configured) — an escape hatch for a professor who'd rather use their own Claude Desktop app than paste an API key into this tool. Its "Baixar skill" link hits `GET /api/skills/enade-it-questions` (session-gated like every other route, same `getSession()`/`isSessionValid()` check), which zips the **tracked** `skills/enade-it-questions/` folder on demand via `adm-zip` and streams it back as `enade-it-questions.skill` (Claude Desktop's own skill-package format — a plain zip with a `Content-Disposition: attachment` filename). Built fresh from the folder on every request rather than shipping a pre-baked binary, specifically so the download can never drift out of sync with `SKILL.md`/`references/` — the same folder `src/lib/aiProviders/shared.js`'s `SYSTEM_PROMPT` is manually condensed from and checked against (see "AI provider adapters" above). Because the route reads from `skills/enade-it-questions/` at runtime (via `process.cwd()`, not a bundled import), that folder being tracked in git — already true, see "AI provider adapters" above — is precisely what makes this download work in any environment the app is deployed to, not just this checkout; don't gitignore it. The generated JSON a professor gets back from Claude Desktop isn't uploaded from this card — the card's own instructions point back to the existing "Enviar arquivo" tab in `QuizImportPanel.jsx`.

### Perfil (`src/app/(dashboard)/perfil/page.jsx`) — where every provider's key is registered

Reached by clicking the username in `Topbar.jsx` (a `<Link href="/perfil">`, not a dropdown). `perfil/page.jsx` stays a Server Component (`listAiIntegrations(user.id)` + `listDriverProviders()`) but renders no sections directly anymore — it passes that data into `src/components/ProfileTabs.jsx` (`'use client'`), which reuses the same folder-style tab CSS/pattern as `QuizImportPanel.jsx` (`.tab-folder`/`.tab-folder-btn`/`.tab-folder-panel`, local `useState`, mostly no URL sync — except the *initial* tab, read once from `?tab=` for the GitHub OAuth redirect, see below). Tabs: **Conta** (read-only), **Plataformas de IA** (a single `src/components/IntegrationManager.jsx` — lists every registered integration as a card and has a "Nova integração" form; CRUD hits `POST`/`PATCH`/`DELETE /api/ai/integrations[/[id]]`; this is the **only** place keys are entered, everything else only ever reads whether an integration has one configured), **GitHub** (`GithubConnection.jsx` — see "GitHub OAuth connection" below), **Atalhos** (`ShortcutsManager.jsx`, CRUD only now — its own standalone export/import buttons were removed, superseded by the page-level control below), **Prompts de IA** (`PromptCustomizer.jsx` — see next section), **Preferências** (placeholder for future non-AI settings).

### Prompt customization (`src/lib/customPrompts.js`, `src/lib/promptResolution.js`, `PromptCustomizer.jsx`)

Every AI capability (`generateQuestions`/`suggestReply`/`improveMessage`) can have a per-user override of its default system prompt, persisted client-side in IndexedDB (`STORE_PROMPTS`, keyPath `'capability'`, added in `src/lib/indexedDb.js`'s `DB_VERSION: 2` upgrade — purely additive, no migration of the existing `shortcuts`/`cache` stores). `src/lib/customPrompts.js`'s `CAPABILITIES` array is the registry (`key`/`label`/`defaultPrompt`, the last imported straight from each capability's own constant, for display only) plus CRUD (`getCustomPrompt`/`getAllCustomPrompts`/`saveCustomPrompt`/`clearCustomPrompt`). Each saved override has a `mode`, chosen per-capability by the user in `PromptCustomizer.jsx`: `'append'` (default — the professor's text is appended after the full default prompt, which still applies) or `'replace'` (the professor's text replaces the default prompt entirely — the UI shows an explicit risk warning here, since structural rules like the JSON schema shape or "exactly one correct answer" stop being guaranteed by the prompt in this mode). `src/lib/promptResolution.js`'s `resolvePrompt(defaultPrompt, customText, mode)` is the pure function implementing this combination — no IndexedDB dependency, so it's safely importable both client-side (`PromptCustomizer.jsx`'s live "prompt final" preview) and server-side.

The trigger components (`QuestionGenerator.jsx`, `MessageList.jsx`, `ComposeMessage.jsx`, `StudentMessageModal.jsx`) each read their own capability's custom prompt via `getCustomPrompt(key)` right before firing their existing fetch, and send it as `customPromptText`/`customPromptMode` alongside their normal payload. The `.../[id]/generate-questions|suggest-reply|improve-message` routes resolve it server-side via `resolvePrompt()` against their own default constant, **then** layer the selected integration's own optional `system_prompt`/`system_prompt_mode` (from `public.ai_integrations`, see "AI provider adapters" above) on top via a second `resolvePrompt()` call, and pass that final result as `systemPrompt` into the adapter call — the adapters themselves never know how many layers went into it. This custom-prompt mechanism stays per-capability and global to the user (not per-integration) — the integration's own `system_prompt` is an *additional* layer on top, not a replacement for it.

### Combined settings export/import (`src/lib/settingsExport.js`, `src/lib/settingsCrypto.js`, `SettingsExportImport.jsx`)

One export/import file covers shortcuts, custom prompts, AI model preferences (`session.aiModels`, unconditionally — see "User-selectable models" below), and — optionally, bundled under one "incluir credenciais" checkbox/password — AI API keys and the GitHub connection (see below). Shortcuts and prompts already live in IndexedDB and are safely client-readable; API keys are a deliberate exception (see `src/app/api/ai/keys/route.js`'s own comment) to the rest of the app's "keys are write-only" design (no other route under `src/app/api/ai/` ever returns a key's plaintext value — confirmed by grep, `key/route.js` only has `POST`/`DELETE`). The GitHub connection's access token, by contrast, already lives in IndexedDB by design (see below) — it isn't a write-only-on-the-server exception like the AI keys, it's just already sitting in the same client-side store shortcuts/prompts use. Either way, including secrets in an export requires the user to set a password: the whole payload (not just the sensitive fields) is then encrypted with `src/lib/settingsCrypto.js`'s `encryptJson`/`decryptJson` (Web Crypto `crypto.subtle`, PBKDF2-SHA256 → AES-GCM 256, no new npm dependency) before ever leaving `exportSettingsFile()`. Without "incluir credenciais" checked, the file is plain JSON, same Blob+`<a download>` pattern as `shortcuts.js`'s original `exportShortcutsFile`. Import (`importSettingsFromFile`) replaces (not merges) shortcuts via `shortcuts.js`'s `replaceAllShortcuts` (extracted from its own `importShortcutsFromFile` so both callers share it), replaces custom prompts via `saveCustomPrompt`, re-POSTs each AI key to the existing `/api/ai/[provider]/key` route, re-POSTs each model preference to `/api/ai/[provider]/model`, and — if the decrypted payload has `github` — writes it straight into IndexedDB via `saveGithubConnection` (no server round-trip needed, unlike AI keys/models).

### GitHub OAuth connection (`src/lib/githubOAuth.js`, `src/lib/githubConnection.js`, `GithubConnection.jsx`) — first of a planned set of GitHub-linking features

Lets a professor connect their profile to a GitHub account, as groundwork for later linking a course to a GitHub repository (board, issues, content) — those linking features don't exist yet; this is only the connection itself. Deliberately architected **differently from Canvas's own OAuth**:

- **Canvas's token**: lives only in the server-side `iron-session` cookie, never reaches the browser (see "Two separate auth models" below).
- **GitHub's token**: the OAuth2 code-exchange still has to happen server-side (`src/lib/githubOAuth.js`, mirroring `canvasOAuth.js`'s shape — `getAuthorizeUrl`/`exchangeCodeForToken`, since GitHub's `client_secret` can't be exposed to the browser either), but the resulting token's *durable* home is IndexedDB (`src/lib/githubConnection.js`, `STORE_GITHUB`), not the session. This was an explicit product decision, not an oversight — the connection is meant to persist independently of the Canvas login session's lifecycle and travel with the browser via the export/import file above, the same as shortcuts and custom prompts.
- **The handoff**: `src/app/github/oauth2/callback/route.js` (note: NOT under `api/`, and NOT the same path as Canvas's own `src/app/oauth2/callback/route.js` — a sibling, unrelated route) exchanges the code, fetches the GitHub user profile (`getGithubUser`), and stashes the result in a **one-time-use** session field (`session.githubPendingConnection`) before redirecting to `/perfil?tab=github&github=connected`. `GithubConnection.jsx` sees that query param, calls `GET /api/github/pending-connection` once (which reads-then-deletes that session field — a real single-use handoff, not durable server storage) and persists the result into IndexedDB itself. The server keeps no lasting copy of a GitHub token anywhere.
- Uses a classic **GitHub OAuth App** (`GITHUB_OAUTH_CLIENT_ID`/`_SECRET`/`_REDIRECT_URI`, default scopes `read:user repo project` via `GITHUB_OAUTH_SCOPES`) — deliberately not a GitHub App (would need an installation flow and webhook infrastructure this doesn't use). Classic OAuth App tokens (`gho_...`) don't expire by default, so unlike Canvas there's no refresh-token logic anywhere in this integration.
- `ProfileTabs.jsx` reads its initial active tab from `useSearchParams().get('tab')` (new — previously always opened on "Conta") specifically so the post-OAuth redirect lands on the GitHub tab; this requires `perfil/page.jsx` to wrap `<ProfileTabs>` in a `<Suspense>` boundary (Next.js's requirement for any `useSearchParams()` consumer).
- Trade-off worth knowing: the GitHub access token sits in **plaintext** in IndexedDB at rest (same as shortcuts/custom prompts — not the AI-keys default), since it's the store the user explicitly asked for. It only gets encrypted at the moment of a deliberate, password-protected export (see above). Future features that actually call GitHub's API should follow the same pattern already used for AI custom prompts: read the token client-side from IndexedDB, send it to one of this app's own API routes per-request, and have that route call GitHub server-side — never call GitHub's API directly from the browser.

### Google Drive preferences sync (`src/lib/googleOAuth.js`, `googleConnection.js`, `googleDriveClient.js`, `googleDriveSync.js`, `GoogleConnection.jsx`)

Lets a professor connect a Google account and back up/restore a subset of their settings — shortcuts,
custom AI prompts, and per-provider AI model choices — via a private `user-preferences.json` file in
the Drive `appDataFolder` (a hidden space Google reserves for app-internal data; it never shows up in
the user's normal Drive UI). This was built from a detailed external functional spec the user provided,
but **deliberately diverges from it in two ways**, both by explicit user decision, not oversight:

1. **What counts as "preferences".** The spec's own `UserPreferences` example (theme/sidebarCollapsed/
   pageSize/defaultCourseId) doesn't correspond to anything that exists in this app. What actually
   persists in IndexedDB today is shortcuts (`shortcuts.js`), custom AI prompts (`customPrompts.js`),
   and AI model choices (`session.aiModels`, exposed via `GET /api/ai/models`) — exactly the same
   non-secret bundle `settingsExport.js` already assembles for the manual local export/import. Rather
   than invent a second, parallel preferences format, `settingsExport.js` was split into
   `buildSettingsPayload({ includeSecrets, password })` / `applySettingsPayload(fileBody, { password })`
   (pure functions, no Blob/File side effects) so both the local download/upload flow and the Drive
   sync flow share the exact same envelope (`{ app, kind, version, exportedAt, encrypted, payload |
   salt/iv/ciphertext }`) and the same PBKDF2→AES-GCM encryption (`settingsCrypto.js`). `exportSettingsFile`/
   `importSettingsFromFile` are now thin wrappers around those two functions; their own behavior is
   unchanged. Because the envelope is shared, `pushToGoogleDrive`/`pullFromGoogleDrive` can optionally
   include the same secrets (AI API keys, GitHub connection) as the local export, gated behind the same
   "incluir credenciais" + password UX already used in `SettingsExportImport.jsx` — the Google integration
   doesn't hardcode a stricter no-secrets rule than the local export already enforces.

2. **OAuth model.** The original spec asked for the Google Identity Services **Token Model**: an
   access token obtained entirely client-side via a GIS popup, never touching the server, no
   `client_secret`, no callback route — explicitly to avoid a refresh-token dance. The user asked
   instead to mirror this app's existing **GitHub OAuth connection** structure (see above): a
   real server-side authorization-code exchange with `client_id`/`client_secret`
   (`src/lib/googleOAuth.js`, same shape as `githubOAuth.js`), a dedicated callback route outside
   `/api/` (`src/app/google/oauth2/callback/route.js`), a one-time session handoff
   (`session.googlePendingConnection`, redeemed once via `GET /api/google/pending-connection`), and
   a durable connection record in IndexedDB (`STORE_GOOGLE`, via `googleConnection.js`) rather than
   the session — all identical in shape to the GitHub integration. The one structural difference:
   **Google's access token expires (~1h), GitHub's classic OAuth token doesn't.** Refreshing needs
   the `client_secret`, which can't reach the browser, so there's a route with no GitHub equivalent —
   `POST /api/google/refresh` — a stateless pass-through that takes the refresh token the browser
   already has, calls `refreshAccessToken()` (mirrors `canvasOAuth.js`'s own refresh, including the
   "Google never returns a new refresh_token on refresh" behavior) server-side, and returns a fresh
   access token without persisting anything. `googleConnection.js`'s `getValidAccessToken()` is the
   single choke point that checks `expiresAt` (same 5-minute safety margin as `proxy.js`'s Canvas
   refresh) and calls that route before any Drive API request. `getAuthorizeUrl()` sets
   `access_type=offline&prompt=consent` specifically to guarantee a `refresh_token` comes back (Google
   only issues one by default on a user's very first consent). Like the GitHub token, Google's access
   + refresh tokens sit in plaintext in IndexedDB at rest — same accepted trade-off documented above
   for GitHub, not a new risk.

`src/lib/googleDriveClient.js` is a thin `fetch`-only wrapper over Drive API v3 (`files.list` scoped to
`spaces=appDataFolder`, multipart `files.create`, media `files.update`/`alt=media` download) — no new
npm dependency, same philosophy as `settingsCrypto.js`'s use of raw Web Crypto. `googleDriveSync.js`'s
`pushToGoogleDrive`/`pullFromGoogleDrive` are two **explicit, separate** actions in `GoogleConnection.jsx`
("Enviar para o Google Drive" / "Baixar do Google Drive"), not one ambiguous "sync now" button — there is
no conflict detection yet (no `revision`/`deviceId`/hash machinery), so an implicit sync direction would
risk a silent overwrite either way. `GoogleConnection.jsx` itself mirrors `GithubConnection.jsx`'s
connect/disconnect/status UI, with the push/pull section reusing `SettingsExportImport.jsx`'s
checkbox+password pattern locally rather than sharing a component.

**Deliberately deferred to a later round** (this is the "connect + manual sync" slice only):
automatic debounced sync after each preference change, conflict detection/resolution UI
(`revision`/`deviceId`/`lastSyncHash`), and validating the remote file's Canvas identity against the
current session before applying it (only matters once multiple devices/auto-sync are in play). None of
these are missing by accident — treat them as a known, intentional gap, not a bug to silently "complete."

`src/proxy.js`'s matcher includes `/google/:path*` and `/api/google/:path*` alongside the equivalent
GitHub entries — same reasoning: a user must already have a valid Canvas session before linking or
syncing Google, and the callback route itself needs the proxy's session-gating too.

## Two separate Canvas auth models — do not conflate them

(A third, independent auth flavor — the GitHub OAuth connection — is documented above under "GitHub OAuth connection"; it deliberately does *not* follow either pattern below, since its token is meant to live client-side.)

- **CLI**: `CANVAS_API_URL` (includes `/api/v1`) + `CANVAS_API_TOKEN`, a long-lived personal access token, read from `.env` via `dotenv`. Never expires, no refresh logic.
- **Web app**: full Canvas OAuth2 authorization-code flow against `CANVAS_DOMAIN` (bare domain, no `/api/v1`) using a Canvas Developer Key (`CANVAS_OAUTH_CLIENT_ID`/`CANVAS_OAUTH_CLIENT_SECRET`/`CANVAS_OAUTH_REDIRECT_URI`). Access tokens expire (~1h); the refresh token does not rotate (Canvas reuses the same one on every refresh — see `src/lib/canvasOAuth.js`). The Canvas token/session is never sent to the browser: it lives only in an encrypted `iron-session` httpOnly cookie (`SESSION_SECRET`, `src/lib/session.js`), read and refreshed server-side (`src/proxy.js`, Route Handlers, Server Components).
- `src/lib/canvasClient.js` is intentionally agnostic to which of the two auth models is in use — it just takes a `{ baseUrl, token }` (plus an optional `onUnauthorized` callback for OAuth's 401-retry). `normalizeBaseUrl()` inside it accepts either convention (`.../api/v1` or bare domain).

## Token refresh design (read this before touching `src/proxy.js`)

`src/proxy.js` is Next.js's Proxy file convention (Next.js 16 renamed `middleware.js` to `proxy.js`; the exported function is `proxy`, not `middleware`). It matches `/`, `/courses/:path*`, `/api/canvas/:path*`, `/questoes/:path*`, and `/api/ai/:path*` (never `/api/auth/*`, or the OAuth callback would be blocked before a session exists). On each matched request it proactively refreshes the access token if it's within 5 minutes of expiring, using `getIronSession(request, response, sessionOptions)` — the signature that actually works here (the `getIronSession(cookies(), ...)` form used in Route Handlers/Server Components has open compatibility issues when called from Proxy, per upstream iron-session GitHub issues).

The 5-minute safety margin is a deliberate choice, not an oversight: it sidesteps ambiguity in whether a proxy-refreshed cookie is visible to a Server Component rendered later in the *same* request — the current request's already-in-hand token is still valid regardless, and the *next* navigation picks up the refreshed cookie from the browser. `canvasClient.js`'s `onUnauthorized` 401-retry is a second, independent backstop for the (rare) case a call is made without going through the proxy-gated paths.

## Validation is intentionally two-tier — do not make schema validation blocking

`src/lib/quizValidation.js`:
- `validateStructural(data)` — **blocking**. The bare minimum to safely call Canvas's API (course_id/quiz_id/questions present, each question has answers with exactly one `is_correct: true`, etc.). Used by the CLI, the client-side file preview, and again server-side in the import route (defense in depth).
- `createSchemaValidator(schemaObject)` + `summarizeSchemaWarnings()` — **non-blocking, ajv against `src/lib/quiz.schema.json`**. This must stay non-blocking: real files under `Questoes/` routinely deviate from the schema (missing `question_model`, extra fields like `nivel` that trip `additionalProperties: false`) and are still legitimate content the tool must keep importing. If you're tempted to make schema conformance mandatory, don't — check `Questoes/DIW-prova1/Gemini/*.json` (no `question_model`) and `Questoes/DIW-prova2/JSON/*.json` (has an extra `nivel` field) first.
- `toCanvasPayload(question)` — the is_correct→answer_weight / answer_comment→answer_comment_html mapping, shared by the CLI and the import route handler.

`quizValidation.js` itself takes the parsed schema as a parameter rather than importing `quiz.schema.json` directly, because the three call sites need different JSON-import syntax: Next's bundler accepts a plain `import ... from '@/lib/quiz.schema.json'` (used in `ImportQuestions.jsx` and any server code), while the unbundled CLI (run directly by `node`) needs `import quizSchema from '../lib/quiz.schema.json' with { type: 'json' }`.

## Question bank data (`Questoes/`)

Unchanged in nature from before this refactor: real exam content across `DIW-prova1`/`DIW-prova2` exam folders, including multiple independent LLM-generated drafts of the same quiz (`claude_quiz/`, `gpt_quiz/`, `Gemini/`) and, in some subfolders, a paired `.md` human-readable version of each `.json` file — keep both in sync when hand-editing. `question_model` values map to Portuguese pedagogical question types: `RU` (Resposta Única), `CM` (Complementação Múltipla), `AR` (Asserção-Razão), `INT` (Interpretação).
